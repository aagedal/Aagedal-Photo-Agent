crs block replacement

Issue 4 — Adobe-faithful by design; confirm each save path behaves
Inspecting crs: values (exiftool 13.55 is installed). Two go-to commands: 
# Every Camera Raw property exiftool models in the file:
exiftool -G1 -s -XMP-crs:all FILE.jpg

# Raw XMP packet, pretty-printed — catches props exiftool doesn't decode
# (mask internals, AlreadyApplied, CompatibleVersion):
exiftool -b -XMP FILE.jpg | xmllint --format -
For RAW files, point these at the .xmp sidecar, not the RAW (we never embed crs into a RAW container). To list just the property names present: 
exiftool -b -XMP FILE.jpg | grep -Eo 'crs:[A-Za-z0-9]+' | sort -u
Develop save drops ACR-only settings intentional
Develop-save in our app on a real ACR-edited JPEG that has Texture / vignette / HSL / brush masks — those settings are removed (replaced by our full develop state); crs:AlreadyApplied="False" and crs:CompatibleVersion are present; ACR preview matches our render. 
# These ACR-only props should be GONE (empty output):
exiftool -s -XMP-crs:Texture -XMP-crs:PostCropVignetteAmount \
  -XMP-crs:HueAdjustmentRed -XMP-crs:LuminanceAdjustmentRed FILE.jpg
# No ACR brush/mask leftovers (expect 0):
exiftool -b -XMP FILE.jpg | grep -c MaskGroupBasedCorrections
# These two should be PRESENT:
exiftool -b -XMP FILE.jpg | grep -E 'AlreadyApplied|CompatibleVersion'
